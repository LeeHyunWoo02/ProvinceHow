# 사람인 JobCount 집계 배치 수집 전략

사람인 오픈 API 의 **하루 500회 호출 제한** 아래에서 JobCount 집계 배치를 어떻게 돌릴지에 대한
전략 문서다. 코드로 확정한 것은 **최소 안전 가드레일 하나뿐**이고, 운영 정책(예산 배분 수치·수집
주기·수집 범위)은 **사용자 사인오프가 필요한 결정**으로 §5 에 분리해 둔다. 여기서 임의로 정하지 않는다.

전체 배치 흐름·실행 절차는 [batch-data-pipeline.md](batch-data-pipeline.md), 채용 소스 스펙·코드
매핑은 [worknet-job-api.md](worknet-job-api.md) 를 본다.

> ⚠️ 이 문서의 모든 수치(기본값·예산 배분·주기)는 **access-key 미발급 상태의 추정치**다.
> 키 발급 후 실제 공고량과 응답을 확인해 튜닝하는 것을 전제로 한다.

---

## 1. 현재 배치 동작과 500회/일 제한의 위험

### 1.1 배치가 하는 일

`jobCountStep` 은 `WorknetJobCountItemReader`(이름은 워크넷이지만 현재 활성 공급자는
`SaraminJobPostingApiAdapter`) 로 채용공고를 **페이지 단위로 끝까지 당겨** (시군구 × 직종)
건수를 집계하고 `job_count` 테이블에 Upsert 한다.

- **페이지 1회 당김 == 외부 API 1회 호출.**
- 사람인 제한: **1일 500회**, 페이지당 최대 110건.
- 배치는 지역·직종별로 개별 호출하지 않고 **전국 공고 피드를 페이지네이션으로 훑는다.**
  따라서 필요한 호출 수 ≈ `전국 공고 수 / 페이지크기(≤110)`.

### 1.2 예산 공유 — 이 전략의 핵심

**사람인 500회/일은 배치 전용이 아니다. on-demand 기능과 공유된다.**

| 소비 주체 | 호출 성격 | 문서 |
| --- | --- | --- |
| JobCount 집계 배치 | 페이지 전수 순회 (대량) | 이 문서 |
| 공고 카드 리스트 (`GET /api/detail`) | 지역별 on-demand 1회, 캐시(6h/네거티브 30m) | redis-conventions |
| 지역 채용 프로필 (`GET /api/detail`) | 지역별 on-demand 1회, 캐시(12h/네거티브 30m) | redis-conventions |

**배치가 예산을 먼저 소진하면 그날 사용자 조회(카드·프로필)가 사람인 429 로 막힌다.**
반대로 트래픽이 몰린 날 배치까지 겹치면 양쪽 다 실패한다. 그래서 배치 예산과 on-demand
예산을 **분리(headroom 확보)** 하는 것이 전략의 출발점이다.

### 1.3 구체적 위험

| 위험 | 내용 |
| --- | --- |
| **예산 소진** | `worknet.job.max-pages` 기본 1000 → 1000 페이지면 1000 회 호출로 500 을 2배 초과. on-demand 가 그날 전부 막힌다 |
| **전수 수집 불가** | 전국 공고가 수만 건이면 110/페이지로도 수백 회가 필요하다. 500 회 예산(그중 배치 몫)만으로는 하루에 전국을 다 못 당길 수 있다 |
| **부분 수집 데이터 손상** | 배치가 예산에 걸려 중간에 끊기면, "이번 스냅샷에 없는 조합은 count=0" 리셋 로직이 **아직 못 당겨온 조합을 사라진 것으로 오인**해 존재하는 일자리 수를 0 으로 덮어쓴다. → §3 에서 가드레일로 차단 |

## 2. 권고 전략

### (a) run 당 호출 예산 상한 + on-demand headroom 분리

배치가 부를 수 있는 페이지 수에 **상한**을 두고, 나머지를 on-demand 몫으로 남긴다.

```
500회/일  =  배치 예산(max-api-calls)  +  on-demand headroom  +  안전 여유
```

- 배치는 **자기 상한을 절대 넘지 않는다**(§3 가드레일로 강제).
- on-demand 는 요청량에 비례하므로 상한을 두지 않되, 배치가 남긴 headroom 안에서 소비된다.
- **트레이드오프**: 배치 상한을 낮추면 on-demand 는 안전하지만 전국 전수 수집이 하루에 안 끝난다
  (→ (c) 로테이션 필요). 높이면 전수 수집은 빨라지지만 on-demand 를 굶길 위험이 커진다.

### (b) 수집 주기 — 트래픽 적은 시간 1회

- 배치는 **사용자 트래픽이 가장 적은 새벽 1회**만 도는 것을 권고한다(예: 03:00, 현재
  `worknet.job.batch.cron` 기본 `0 0 3 * * *`).
- 새벽에 배치가 예산을 쓰더라도 하루가 바뀌면(사람인 일일 카운터 리셋) 낮 동안의 on-demand 는
  새 예산을 쓴다. **일일 리셋 경계와 배치 시각을 붙여** on-demand 가 배치 소비 후 회복할 시간을 준다.
- **트레이드오프**: JobCount 는 legacy 집계(§4)라 신선도 요구가 낮다. 매일 돌 필요가 없다면
  주 1~2회로 낮춰 예산을 아끼는 선택도 가능하다(정책 결정 → §5).

### (c) 수집 범위 우선순위 — 전수 대신 로테이션/체크포인트

하루 예산으로 전국이 안 끝나면 두 가지 축소 전략이 있다.

| 방식 | 설명 | 트레이드오프 |
| --- | --- | --- |
| **우선 지역군** | 인구·수요가 큰 시군구부터 수집하고 나머지는 후순위 | 후순위 지역 JobCount 가 오래된 채로 남는다. "우선 지역군" 정의가 기획 결정 |
| **여러 날 rotation** | 전국을 N 등분해 하루에 1/N 씩, N 일에 한 바퀴 | 구현 필요(현재 Reader 는 전수 순회만 한다). 체크포인트/커서 저장 로직 추가 = 별도 작업 |
| **checkpoint-resume** | 중단된 페이지부터 다음 run 이 이어받음 | **현재 구조와 상충**: Reader 는 부분 집계 이어붙이기를 금지한다(건수가 틀림). resume 하려면 "당일 전체를 원자적으로 반영" 모델을 "지역 파티션 단위 반영" 으로 바꿔야 한다 = 스냅샷 교체 정책 재설계 |

> 현재 코드는 **전수 순회 + 완주 시에만 반영** 모델이다. (c) 의 rotation/resume 은 스냅샷 교체
> 정책과 Reader 구조를 함께 바꿔야 하는 **별도 설계 작업**이며 이 문서에서 코드로 확정하지 않는다.

### (d) job-mid-code 집계로 호출·카디널리티 절감

직종을 세부 job_cd 가 아니라 **job-mid-code(대분류 21개)** 로 매핑하도록 전환했다
([worknet-job-api.md](worknet-job-api.md) / saramin-job-api.json).

- 집계 카디널리티가 (시군구 264 × 직종 21) 로 낮아져 **결과 행·메모리·0 리셋 대상이 준다.**
- 다만 **호출 수 자체는 줄지 않는다** — 배치는 어차피 전국 피드를 페이지로 훑기 때문이다.
  카디널리티 절감의 이득은 저장·집계 쪽이지 호출 예산 쪽이 아니다. 호출 절감은 (a)·(c) 가 담당한다.

## 3. 최소 안전 가드레일 (구현됨)

**run 당 최대 API 호출 수 상한**을 설정값으로 추가했다. 정책이 아니라 **예산 초과를 물리적으로
막는 안전장치**다.

| 항목 | 값 |
| --- | --- |
| 설정 키 | `apis.saramin.batch.max-api-calls` (env `SARAMIN_BATCH_MAX_API_CALLS`) |
| 기본값 | `400` (보수적. 500 미만으로 두어 on-demand 에 headroom 을 남긴다) |
| 적용 지점 | `WorknetJobCountItemReader` |
| 기존 키와의 관계 | `worknet.job.max-pages`(기본 1000)는 **삭제하지 않고 유지**. 실제 상한 = `min(max-pages, max-api-calls)`. max-pages 는 메모리(중복 제거 집합) 상한, max-api-calls 는 **호출 예산 가드레일** 로 역할을 분리했다 |

### 3.1 상한 도달 시 동작 — 부분 수집 안전성

가장 중요한 부분이다. Reader 는 페이지를 끝까지 당긴 **뒤** "사라진 조합 count=0" 리셋을 적용한다.
따라서 상한에 걸려 **수집이 완주하지 못하면** 부분 스냅샷이 리셋을 오작동시킨다(§1.3).

이를 막기 위해 가드레일은 **"상한 도달로 수집이 불완전하면 이번 run 결과를 통째로 반영하지 않는다"**
쪽으로 동작한다.

- 수집 완주(빈 페이지 도달 또는 `hasNext=false`) → 정상적으로 집계·Upsert·0 리셋 적용.
- 상한(`min(max-pages, max-api-calls)`)에 걸렸는데 아직 다음 페이지가 남음 → **행을 하나도
  내보내지 않는다.** Upsert 도, 0 리셋도 일어나지 않아 **기존 데이터가 그대로 보존**된다. 사유는
  `WARN` 로그로 남긴다(`apiCalls`, `readPostings` 포함).

이 동작은 `isConfigured()==false`(인증키 미설정) 시 아무 행도 내보내지 않는 기존 안전 경로와 같은
원칙이다. **"불완전하면 반영하지 않는다"** 를 일관되게 적용한다.

> 부수 효과로, 기존 `max-pages` 만 있던 시절의 잠재 위험(상한 도달 후에도 부분 집계를 반영하던
> 동작)도 함께 제거됐다. 이제 어떤 상한이든 완주하지 못하면 반영하지 않는다.

테스트: `WorknetJobCountItemReaderTest`
- `abandonsRunWhenCallBudgetExhaustedBeforeCompletion` — 예산(2)에 걸리면 2회만 호출하고 행 미출력,
  0 리셋을 위한 저장소 조회조차 하지 않음(기존 데이터 무손상).
- `appliesResultsWhenCollectionCompletesWithinBudget` — 예산 안에서 완주하면 정상 집계 + 0 리셋 적용.

### 3.2 정책은 발명하지 않았다

- **재시도·멱등성·알림 정책은 손대지 않았다**(CLAUDE.md). 멱등성은 기존 Upsert(`count=VALUES(count)`)로
  이미 보장된다. 재시도/알림은 정의된 바 없어 추가하지 않았다.
- **스케줄링 주기·cron 은 코드로 바꾸지 않았다.** §2(b)·§5 의 권고로만 남긴다.

## 4. 권고 파라미터 표 (기본값 제안 — 튜닝 전제)

| 파라미터 | 키 | 제안 기본값 | 근거 / 튜닝 방향 |
| --- | --- | --- | --- |
| 배치 호출 예산 상한 | `apis.saramin.batch.max-api-calls` | **400** | 500 미만으로 on-demand headroom 확보. 실제 공고량·on-demand 트래픽 확인 후 조정 |
| 페이지 크기 | `worknet.job.page-size` | 100 | 사람인 페이지당 최대 110. 110 으로 올리면 같은 호출 수로 더 많이 당긴다(호출 절감) |
| 메모리 상한 | `worknet.job.max-pages` | 1000 | 중복 제거 집합 상한. 실제 상한은 max-api-calls 가 더 작아 이 값이 바인딩되지 않는다 |
| 배치 주기 | `worknet.job.batch.cron` | `0 0 3 * * *` | 트래픽 적은 새벽. 신선도 요구 낮으면 주 1~2회로 완화 가능 |
| 배치 활성화 | `worknet.job.batch.enabled` | `false` | 키·전략 확정 전까지 비활성 유지 권고 |

> page-size 를 110 으로 올리면 400 회 예산으로 최대 약 44,000 건까지 당길 수 있다. 전국 공고가
> 이보다 많으면 하루에 전수 수집이 불가하며 §2(c) 로테이션이 필요하다 — 실제 규모는 키 발급 후 확인.

## 5. 사용자 사인오프가 필요한 결정

아래는 **운영 정책**이라 코드로 임의 확정하지 않았다. 확정 후 설정값·주기·범위를 정한다.

| 결정 항목 | 무엇을 정해야 하나 | 현재 상태 |
| --- | --- | --- |
| **예산 배분 수치** | 500회/일 중 배치 몫 vs on-demand headroom 을 몇 대 몇으로? | 가드레일 기본값 400 은 **임시 안전 상한**일 뿐. 실제 배분은 미정 |
| **수집 주기** | 매일 새벽 1회 vs 주 N회? JobCount 신선도 요구 수준은? | cron 기본값만 존재. 정책 미확정 |
| **수집 범위** | 하루 예산으로 전수 불가 시 — 우선 지역군? N일 rotation? "우선 지역" 정의는? | 현재는 전수 순회. 축소 전략 미구현 |
| **rotation/resume 도입 여부** | 도입 시 스냅샷 교체 정책·Reader 구조 재설계 필요(별도 작업) | 미착수. §2(c) 트레이드오프 참조 |

## 6. 남은 위험

- 위 모든 수치는 **access-key 미발급 상태의 추정**이다. 전국 실제 공고량을 모르면 400회로 전수가
  되는지 판단할 수 없다. 키 수령 후 1회 실측이 선행돼야 한다.
- **전수 미완 시 데이터 미갱신**: 가드레일이 부분 수집을 안전하게 버리므로, 예산이 부족하면
  JobCount 가 **오래된 채로 남는다**(손상되지 않지만 갱신도 안 된다). 이는 데이터 손상보다 안전한
  선택이지만, 신선도가 필요하면 §2(c) rotation 도입이 필요하다.
- 배치와 on-demand 가 **같은 일일 카운터**를 공유하므로, 배치 상한을 지켜도 on-demand 트래픽이 큰
  날에는 배치가 성공해도 낮 시간 on-demand 가 부족할 수 있다. 예산 배분(§5) 확정이 필요하다.
